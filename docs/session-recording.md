# 联调录制使用指南

本指南对应当前版本「联调录制」页面，介绍从真实业务流量录制，到保存客户端用例、生成 Mock 和离线回测的完整流程。推荐先录制一笔交易，确认请求响应配对正确，再扩大录制范围。

阅读顺序：首次使用先看第 1～4 节；Linux 服务器实时录制看第 5 节；本机录制和文件导入看第 6～7 节；检查与导出看第 8～10 节；离线模拟对方看第 11 节；遇到问题查看第 13 节。

## 1. 先选择采集方式

在 TestTool 主窗口打开「联调录制」，通过「采集方式」选择入口。

| 采集方式 | 适用场景 | 业务目标地址是否需要修改 | 工具要求 |
| --- | --- | --- | --- |
| 本机被动抓包 | 业务程序运行在本机，或本机网卡能看到对应流量 | 不需要 | 本机 TShark、网卡抓包权限；Windows 实时采集需 Npcap |
| SSH Linux 远端抓包 | 业务程序运行在可 SSH 登录的 Linux 服务器 | 不需要 | 本机 TShark、OpenSSH；远端 tcpdump 和抓包权限 |
| 导入 pcap / pcapng | 已经在服务器或 Wireshark 中录好抓包文件 | 不需要 | 本机 TShark；无需本机网卡抓包权限 |
| 代理录制（已有功能） | 可以让业务流量经 TestTool 转发 | 需要调整连接地址或转发路径 | 无需 TShark；TestTool 需要能访问真实上游 |

被动抓包必须发生在能看到流量的地方。例如程序运行在 Linux 服务器上，应使用该服务器采集、抓包文件导入，或配置了端口镜像的采集网卡。电脑仅能访问该服务器，不代表电脑网卡能看到服务器与其他单位之间的连接。

SSH 远端模式的实际数据流是：

```text
业务流量：Linux 业务程序 ⇄ 原目标服务
                      ↓ 旁路观察
采集通道：远端 tcpdump → SSH 原始 pcap 流 → 本机 TShark → 请求响应会话
```

远端无需安装 TShark；本机无需为 SSH 模式配置网卡抓包权限。远端不会先生成完整文件再下载，而是持续传输、持续解析。SSH 采集不会改变业务程序访问的目标地址。

## 2. 录制前需要确认的信息

开始之前，准备以下信息：

| 信息 | 示例 | 用途 |
| --- | --- | --- |
| 业务服务端 IP | `10.20.30.40` | 可选 IP 过滤、确认真实目标 |
| 业务服务端端口 | `8000` | 采集范围及请求方向判断 |
| 协议 | TCP、HTTP/1.1、WebSocket | 决定报文解析方式 |
| TCP 报文边界 | 5 位 ASCII 长度头 | 从字节流拆出业务报文 |
| 报文编码 | UTF-8、GBK | 文本查看与 JSON 解析 |
| 请求响应关联字段 | `$.requestId` | 多笔请求并发、响应乱序时正确配对 |
| 采集位置 | 本机、Linux 服务器、现有文件 | 选择采集方式 |

**服务端端口填写业务服务提供方的端口，而不是客户端随机分配的源端口。**

例如：

```text
我方 10.10.1.5:43526 → 对方 10.20.30.40:8000
```

服务端端口填 `8000`，可选 IP 过滤填 `10.20.30.40`。如果对方调用我方监听在 `9000` 的服务，就填 `9000`，即使这次流量是从远端进入本机。

当前一次录制配置一个服务端端口。不同端口、协议、编码或分帧方式，建议分别建立录制会话。

## 3. 本机和服务器的工具准备

### 3.1 本机 TShark

TShark 是 Wireshark 的命令行解析工具，当前不随 TestTool 安装包分发。

Windows 通常位于：

```text
C:\Program Files\Wireshark\tshark.exe
```

可以在 PowerShell 中检查：

```powershell
& "C:\Program Files\Wireshark\tshark.exe" --version
```

Linux/macOS 可以检查：

```bash
tshark --version
```

在页面「本地 TShark」填可执行文件完整路径。留空时，程序会从 PATH 以及常见 Windows/macOS Wireshark 安装目录查找。

此字段在所有抓包模式下都表示**本机路径**。不要因为选择了 SSH 模式，就把 Linux 服务器上的路径填到这里。

### 3.2 本机实时采集的网卡和权限

查看网卡：

```bash
tshark -D
```

Windows PowerShell：

```powershell
& "C:\Program Files\Wireshark\tshark.exe" -D
```

把输出中的网卡编号或名称填入「采集网卡」。

| 流量位置 | 常用网卡选择 |
| --- | --- |
| Linux 本机访问外部服务器 | 实际业务网卡，或 `any` |
| Linux 本机进程互相访问 | `lo`，或 `any` |
| Windows 本机访问外部服务器 | 实际使用的以太网/Wi-Fi 网卡 |
| Windows 本机回环连接 | Npcap loopback 网卡，以 `tshark -D` 的输出为准 |
| macOS 本机回环连接 | 通常为 `lo0`，以网卡列表为准 |

Windows 本机实时采集需要 Npcap；Linux/macOS 需要为采集账户配置相应抓包权限。仅解析远端 pcap 流或导入文件时，不需要本机网卡抓包权限。

### 3.3 SSH 远端采集准备

本机检查 OpenSSH 客户端：

```bash
ssh -V
```

在终端先登录服务器，完成主机指纹确认，并确认密钥认证可用。使用界面中相同的用户名、SSH 端口及私钥，例如：

```bash
ssh -p 22 -i /path/to/id_ed25519 tester@10.10.1.5
```

Windows 私钥路径可以填写 `C:\Users\你的用户名\.ssh\id_ed25519`。私钥字段留空时使用 OpenSSH 默认配置、默认密钥或 ssh-agent。私钥需要口令时，应先让 ssh-agent 加载它；当前界面不会交互询问口令或登录密码。

检查远端 tcpdump：

```bash
ssh -T -p 22 -i /path/to/id_ed25519 tester@10.10.1.5 tcpdump --version
```

版本命令成功仅证明程序存在，还需要确认该 SSH 账户可以**直接、非交互执行抓包**。例如在服务器终端运行：

```bash
tcpdump -i any -nn -c 1 'tcp port 8000'
```

然后发起一笔匹配流量，确认能够捕获；没有流量时该命令会等待，可用 Ctrl+C 结束。如果出现权限不足，应由服务器管理员配置采集权限或安排具有权限的账户。

当前程序不会自动执行 sudo。如果服务器只能通过 `sudo tcpdump` 抓包，而 SSH 用户直接执行 tcpdump 会失败，则当前 SSH 实时模式也会失败。可以先由有权限的人员在服务器生成 pcap 文件，再使用文件导入模式。

「远端 tcpdump」填服务器上的可执行文件路径，例如 `/usr/sbin/tcpdump`；留空使用 `tcpdump`。这里不能填写 `sudo tcpdump` 或整段 shell 命令，程序会把它当成一个可执行文件路径。

SSH 不跳过主机密钥校验，不申请交互终端，使用密钥/agent 的非交互认证。

## 4. 公共参数怎样填写

### 4.1 参数说明

| 页面字段 | 填写方法 |
| --- | --- |
| 会话名称 | 建议包含对接单位、接口和结果，例如「某单位-余额查询-成功响应-2026-10-17」 |
| 服务端端口 | 真实业务服务端端口；不是 SSH 端口，也不是客户端临时源端口 |
| IP 过滤 | 可选的单个 IPv4/IPv6 地址；不是域名、CIDR 或过滤表达式；可匹配连接任一端 |
| 协议 | 私有 TCP 选 TCP；HTTP 明文选 HTTP/1.1；WebSocket 明文选 WebSocket |
| 文本编码 | 按真实业务协议选择，不能只根据当前显示是否可读猜测 |
| TCP 分帧 | TCP 模式需要配置；HTTP/WS 使用协议解析器，不使用此下拉项分帧 |
| 长度头位数 | 仅 ASCII 长度头模式使用，支持 1～12 位 |
| 分隔符（Hex） | 仅分隔符模式使用，填写字节的十六进制表示 |
| 关联字段 | 留空按连接内请求顺序关联；填写 JSON 路径时按业务字段关联 |
| 空闲超时（秒） | 用于代理和回放连接，并作为导出客户端的超时参数；不是抓包自动停止计时，也不是按空闲时间拆包 |
| Mock / 代理监听地址、端口 | 被动录制时不占用此端口；之后启动录制 Mock 时使用 |
| 上游地址、端口 | 仅代理录制使用；被动录制生成客户端时，取选中连接实际访问的服务地址 |

修改顶部协议、编码或分帧参数不会重新解析已经保存的会话。文件录错参数，可以按正确参数重新导入成新会话；实时录制录错参数，需要重新采集。

### 4.2 TCP 的三种分帧方式

**ASCII 长度头**适用于「固定宽度的十进制 ASCII 长度 + 正文」。例如线路数据：

```text
00005HELLO
```

填写长度头位数 `5`，解析得到正文 `HELLO`。长度表示正文的**字节数**，不包含长度头；中文等多字节字符不能按字符数计算。

当前此选项不支持二进制整数长度头、十六进制长度头，也不支持“长度包含头自身”的变体。

**分隔符**适用于每条报文以固定字节序列结束：

| 协议结束符 | 分隔符（Hex） |
| --- | --- |
| LF 换行 | `0a` |
| CRLF 换行 | `0d0a` |
| ETX | `03` |

例如 `HELLO\r\n`，填 `0d0a`，正文解析为 `HELLO`，原始线路数据仍保存结束符。分隔符支持 1～64 字节。当前按字节直接查找分隔符，不处理业务协议中的转义规则。

**连接关闭（每方向一条）**适用于一个方向的完整数据需要到发送方关闭发送方向时才能确定结束的协议。被动抓包必须捕获真实 FIN；点击「停止并保存」不能代替 FIN。

如果双方都先等待对方返回、又不关闭发送方向，不能使用此方式。长连接一问一答一般应使用协议已有的长度头或分隔符。

### 4.3 怎样关联请求和响应

严格一问一答、同一连接请求和响应保持顺序时，可以留空「关联字段」。

同一连接存在多笔未完成请求、响应可能乱序时，应填写双方报文都有的 JSON 流水号字段。例如：

```json
请求：{"requestId":"Q1001","tradeCode":"QUERY","account":"A001"}
响应：{"requestId":"Q1001","code":"0000","balance":100}
```

关联字段填：

```text
$.requestId
```

也支持嵌套点路径和数组数字索引，例如 `$.header.serialNo`、`$.items.0.id`。不支持完整 JSONPath、正则表达式、XML 路径或二进制偏移提取；关联字段一次填写一个路径。

关联只在同一连接内自动完成。跨连接的异步回调需停止录制后人工配对。字段缺失、JSON 解析失败、同一连接多个未完成请求使用相同流水号时，程序不会猜测唯一归属；应检查「全部消息」并根据实际业务修正。

“录制时关联字段”与“回放规则匹配字段”作用不同：前者找出真实请求对应的真实响应，后者决定收到新请求时选哪条录制响应。

## 5. Linux SSH 实时录制：完整示例

假设：

```text
业务程序所在 Linux：10.10.1.5
对方服务：10.20.30.40:8000
SSH 用户：tester
SSH 端口：22
协议：TCP，5 位 ASCII 长度头，UTF-8，JSON 流水号 requestId
TestTool 运行在你的电脑上
```

### 5.1 填写界面

| 字段 | 示例值 |
| --- | --- |
| 采集方式 | SSH Linux 远端抓包 |
| SSH 主机 | `tester@10.10.1.5` |
| SSH 端口 | `22` |
| SSH 私钥 | 本机私钥路径，或留空使用默认配置/agent |
| 采集网卡 | `any`，或实际承载业务流量的远端网卡 |
| 服务端端口 | `8000` |
| IP 过滤 | `10.20.30.40` |
| 本地 TShark | 本机 tshark 可执行文件路径，或留空自动查找 |
| 远端 tcpdump | 例如 `/usr/sbin/tcpdump`，或留空使用 `tcpdump` |
| 会话名称 | 某单位-查询接口-正常响应 |
| 协议 | TCP |
| 文本编码 | UTF-8 |
| TCP 分帧 | ASCII 长度头 |
| 长度头位数 | `5` |
| 关联字段 | `$.requestId` |

也可在 SSH 主机填 OpenSSH 配置中的主机别名；SSH 端口字段仍需填实际端口。

### 5.2 开始录制

1. 点击「开始远端抓包」。
2. 检查状态栏是否出现工具、认证、网卡或权限错误。「已启动」表示采集进程已启动，并不代表已经捕获到业务报文。
3. **让需要录制的业务连接在采集开始后新建**，再触发第一笔真实联调。对于已有连接池或长连接，需要按测试环境允许的方式重建目标连接，不能只在旧连接上继续发报文。
4. 在界面观察采集包数、连接和请求响应是否出现。列表约每 2 秒刷新一次，也可以点击「刷新」。
5. 建议先发送一笔查询，核对内容及配对，再补录成功、失败、空结果等不同业务情况。
6. 交易完成后尽量正常结束测试连接，等待最后的响应/关闭报文被采集，再点击「停止并保存」。
7. 等待状态显示录制结束、会话已保存，再进行人工配对、用例导出或回放规则操作。

停止采集不关闭真实业务连接；停止动作终止的是采集通道、本地解析进程和远端采集进程。程序不会主动向真实业务连接发送 FIN/RST。

### 5.3 核对录制结果

先检查「连接」是否有错误，再检查「请求 / 响应」中的交易是否为 `complete`。选择交易，核对来源、实际服务地址、请求、响应和耗时是否符合真实联调。

当前不能使用与 SSH 管理端口相同的业务采集端口。例如 SSH 使用 22 时，服务端端口也填 22 会被拒绝，以避免采集传输反复被录入。此类场景改用服务器独立抓文件后导入。

## 6. 本机被动抓包

1. 打开「联调录制」，采集方式选「本机被动抓包」。
2. 用 `tshark -D` 查找实际业务网卡，填写「采集网卡」。Linux 可以用 `any`；本机回环连接选相应回环网卡。
3. 填「服务端端口」及可选 IP 过滤。例如本机客户端访问 `10.20.30.40:8000`，填端口 `8000`，IP 可填 `10.20.30.40`。
4. 填本地 TShark 路径，选择协议、编码、TCP 分帧和关联字段。
5. 点击「开始被动抓包」，让业务建立新连接，再进行真实交易。
6. 核对是否出现请求响应。完成后「停止并保存」，检查连接及交互状态。

此模式同样适用于别人访问本机业务服务：填写本机业务服务的监听端口，选择能看见入站和出站流量的网卡。TestTool 不与业务服务争抢监听端口。

## 7. 在服务器录文件，再导入

适用于不能使用 SSH 密钥自动采集、只能人工 sudo 抓包，或需要让服务器管理员协助录制的环境。

### 7.1 在 Linux 上生成 pcap

先开始抓包，再建立业务连接：

```bash
sudo tcpdump -i any -s 0 -U -w session.pcap 'tcp port 8000 and host 10.20.30.40'
```

完成联调后，等待最后的响应和连接结束，再按 Ctrl+C。查看 tcpdump 结束统计是否提示丢包，然后把文件复制到运行 TestTool 的电脑。

例如本机终端执行：

```bash
scp -P 22 tester@10.10.1.5:/path/to/session.pcap ./session.pcap
```

如果文件由 root 创建，先由有权限的人员安排可读取的文件副本。不要把有权限读取误当成已经获得实时抓包权限。

如果流量存在 IP 分片，按端口过滤可能漏掉不带 TCP 头的后续分片。可由采集人员扩大为相关主机的完整 IP 流量后导入，例如：

```bash
sudo tcpdump -i any -s 0 -U -w session.pcap 'host 10.20.30.40'
```

再由 TestTool 按业务服务端口筛选解析。

### 7.2 在 TestTool 导入

1. 采集方式选「导入 pcap / pcapng」。
2. 点击「选择抓包文件…」，选择文件。
3. 填服务端端口、可选 IP 过滤、本地 TShark 路径。
4. 按录制时的真实协议设置编码、分帧、关联字段。
5. 点击「导入抓包文件」，等待后台导入结束。
6. 核对会话和交互结果。

导入时无需填写 SSH 信息和采集网卡，也无需本机抓包权限。再次导入会创建新会话；修改顶部参数不会自动重新解析上次的会话。

文件导入与实时录制使用同一套关联和回放流程。消息时间与耗时来自抓包文件中的时间，不是导入所花的时间。

## 8. 查看和修正会话

### 8.1 左侧会话列表

| 操作 | 作用 |
| --- | --- |
| 刷新 | 从数据库刷新会话和当前详情 |
| 加载配置 | 把所选会话的录制参数恢复到顶部；不重新采集、不重新解析 |
| 导出 JSON | 导出所选会话完整归档，不仅是当前显示的几百条数据 |
| 删除 | 删除所选录制会话及关联录制数据，应先确认归档情况 |

选择会话本身与「加载配置」不同。查看历史后，如果要按同样配置再次录制，先点击「加载配置」，修改名称，再开始新录制。

### 8.2 右侧四个页面

| 页面 | 主要用途 |
| --- | --- |
| 请求 / 响应 | 查看已发起请求、配对结果、来源、上游、耗时；生成客户端或 Mock |
| 全部消息（含未关联响应） | 查看原始负载片段、业务报文、未配对响应、握手与控制事件 |
| 连接 | 判断采集是否完整、是否存在序列缺口、解析或连接错误 |
| 录制 Mock 规则 | 管理回放规则、选择多规则命中策略、启动和停止录制 Mock |

选择交易或消息后，下方显示文本、业务数据 Hex、元数据或原始线路字节。当前事件里的“原始”指捕获的 TCP 负载或解析出的协议线路数据，不是完整以太网/IP 包文件。

### 8.3 常见状态

| 状态 | 含义和处理 |
| --- | --- |
| 会话 `recording` | 录制尚未结束 |
| 会话 `stopped` | 已停止；仍需检查每笔交易是否完整 |
| 交互 `pending` | 已有请求，当前还未配到响应 |
| 交互 `complete` | 已得到完整请求和对应响应，可进一步生成回放规则 |
| 交互 `no_response` | 被动采集结束时未配到响应，可能是确实未返回，也可能尚未完整采集 |
| `incomplete` | 发现截断、缺口、缺失握手、TLS、解析或持久化问题，应查看具体错误 |
| 连接 `closed` | 已观察到双方正常关闭 |
| 连接 `capture_stopped` | 采集结束时业务连接仍未完全关闭；不等同于发现报文损坏 |

代理模式还可能显示 `timeout`、`unanswered` 等状态，仍以具体连接错误和请求响应为准。

一个会话可以包含多条连接。会话出现 `incomplete` 时，检查具体错误及每条连接，不要仅根据其他交易有正常响应就认为整个录制完整。

### 8.4 人工配对

1. 先停止录制或 Mock，并等待文件导出结束。
2. 进入「全部消息（含未关联响应）」。
3. 点击「人工配对请求与响应」。
4. 根据连接标识、序号、正文和流水号选出真实对应的请求及响应。
5. 确认后回到「请求 / 响应」复核。

允许在同一会话中跨连接配对，适合异步回调；一个响应只能配给一条请求，重新分配响应会解除其旧配对。

原始 TCP 片段、WebSocket 握手和控制事件不能配成业务交易。被动抓包连接已经判定不完整时，也不能通过人工配对把它改成可正常回放的交互。

界面最多显示最近 500 条交互/消息，人工配对下拉项来自当前展示的消息。大量流量应分批录制。详情最多预览前 64 KB；导出包含已持久化的全部记录。会话开始时间列使用 UTC，消息时间按本机时区显示。

## 9. 保存成客户端回测用例

1. 停止录制，选择所需会话。
2. 在「请求 / 响应」选择一条 `complete` 交易。
3. 点击「生成客户端用例」。
4. 输入新的集合名称并确认。
5. 切换「协议测试」，找到新集合及目标。
6. 检查目标地址、端口、编码、长度头或 HTTP 请求参数，按当前测试环境调整后发送。

被动抓包导出的目标地址取该连接真实访问的服务地址。例如录制的是 `10.20.30.40:8000`，导出的客户端仍指向此地址；需要请求 Mock 时，应主动改成 Mock 的地址和端口。

请求保存为可编辑预设，录制响应和原始字节保存到测试历史，便于人工对照。**生成客户端用例不代表自动配置好了字段级回归断言，也不会自动批量重放整段业务流程。**

当前一次操作导出一条选中交易。分隔符 TCP、二进制 WebSocket、不能无损转成文本的报文，或某些压缩 HTTP 请求不能导出到现有文本客户端；使用录制页回放保留原始内容。

## 10. 保存成固定 Mock

适合“先返回一个已知响应，验证调用方是否能继续处理”的简单场景。

1. 在「请求 / 响应」选完整交易。
2. 点击「保存为固定 Mock」。
3. 输入集合名称。
4. 在「协议测试」找到生成的集合、目标和关联 Mock 服务端配置。
5. 检查监听地址、端口、响应内容及延迟，再手动启动 Mock。
6. 让调用方访问该 Mock 地址，发送请求，确认返回录制响应。

此操作创建配置，不会自动启动监听。固定 Mock 主要固定返回一份响应；需要根据不同请求自动挑选不同录制结果时，使用下面的「录制 Mock 规则」。

## 11. 使用录制 Mock 规则模拟对方

这是对方网络不可达时，按真实请求选择历史响应的主要用法。

### 11.1 从交易生成规则

1. 停止录制，选择一条完整交易。
2. 点击「生成回放规则」。
3. 输入规则名称。
4. 选择「精确匹配正文」或「JSON 字段匹配」。
5. 需要时填写「匹配字段（逗号分隔）」和「回填字段（逗号分隔）」。
6. 设置延迟（毫秒），确认保存。
7. 对需要覆盖的其他交易重复上述操作。

延迟范围为 `0～60000` 毫秒，默认采用该交易录制耗时并限制到 60000 毫秒。需要快速功能验证可以设为 `0`。

### 11.2 怎样选择匹配方式

| 匹配方式 | 行为 | 适合场景 |
| --- | --- | --- |
| 精确匹配正文 | 正文字节必须与录制时完全一致 | 请求内容固定、无动态流水号 |
| JSON 字段匹配 | 只比较指定路径的 JSON 值 | 请求中含流水号、时间戳等动态字段 |

HTTP 无论选择哪种方式，都会同时匹配方法和完整路径（包含查询串），请求头不参与匹配。因此即使 JSON 匹配字段不包含时间戳，URL 查询串中的动态时间戳不同仍可能不命中。

WebSocket 还会匹配文本/二进制消息类型。精确正文匹配对空格、换行和 JSON 字段顺序都敏感；JSON 字段匹配则按指定值比较。

### 11.3 流水号回填示例

真实录制得到：

```json
请求：{"tradeCode":"QUERY","requestId":"old-001","account":"A001"}
响应：{"requestId":"old-001","code":"0000","balance":100}
```

生成规则时填写：

```text
匹配方式：JSON 字段匹配
匹配字段：$.tradeCode,$.account
回填字段：$.requestId
```

当前收到新请求：

```json
{"tradeCode":"QUERY","requestId":"new-999","account":"A001"}
```

Mock 返回：

```json
{"requestId":"new-999","code":"0000","balance":100}
```

回填是从**当前请求相同路径**复制到响应。请求必须包含该字段，响应中该字段的父级结构必须存在；末级字段会被写入或覆盖。当前不能配置“请求的 `$.header.id` 回填到响应的 `$.result.requestId`”这种不同路径映射。

回填会重新序列化 JSON，并重新生成 TCP 长度头或 HTTP Content-Length；不保证保持原来的空白与字段格式，也不会自动重新计算业务签名、MAC 或校验字段。压缩 HTTP 响应不能直接回填 JSON。

### 11.4 多条规则都命中时

在「录制 Mock 规则」选择策略：

| 策略 | 行为 |
| --- | --- |
| 多条命中时报错 | 发现匹配歧义，不随意选择一条 |
| 多条命中按连接内顺序回放 | 按命中规则的创建顺序返回，每个连接有独立位置；用完后报错，不循环 |

更推荐先让匹配条件能唯一确定响应。顺序策略适合同一连接重复相同请求、需要依次返回不同结果的测试，不是完整业务状态机；重新建立连接会重新开始该连接的顺序。

当前规则页面支持新增、删除；需要修改规则时，删除旧规则，再从对应交易生成新规则。规则变化后需要重启 Mock 才生效。

### 11.5 启动离线 Mock

1. 选择有回放规则的历史会话。
2. 根据调用方位置设置顶部「Mock / 代理监听地址」和端口。
3. 切换「录制 Mock 规则」，点击「在当前监听地址启动 Mock」。
4. 检查状态是否启动成功、端口是否被占用。
5. 把离线测试调用方的目标改成 Mock 地址，发送对应请求。
6. 完成后点击「停止 Mock」。

| 调用方位置 | 监听及访问示例 |
| --- | --- |
| 调用方和 TestTool 同一电脑 | 监听 `127.0.0.1:19000`，调用方访问 `127.0.0.1:19000` |
| 调用方在 Linux 服务器，TestTool 在电脑 | 监听电脑可达地址或 `0.0.0.0:19000`，调用方访问电脑实际 IP 的 `19000` 端口 |

`0.0.0.0` 是监听所有 IPv4 网卡的地址，不能作为远端调用目标。需要其他机器访问时，应确认对应地址、路由和端口可达。

Mock 的监听地址和端口取顶部当前值；协议、编码、分帧和超时取**选中会话保存的配置**。不能只修改顶部协议或长度头，就把旧会话转换为另一种协议回放。

无命中规则时，HTTP 返回 404，其余协议关闭连接并提示原因。Mock 不会自动转发到真实上游，也不会自动录制缺失用例。

录制阶段可以保持业务原目标不变；离线使用新 Mock 地址时，需要让调用方访问该 Mock。若调用地址不能调整，应由测试环境自行安排地址/路由映射，TestTool 不会自动劫持原目标 IP。

## 12. 归档和下次继续使用

- 录制会话、连接、业务报文、配对和规则保存在当前 SQLite 数据库，停止后无需再点击其他保存按钮。
- 重启 TestTool 并使用同一个数据库，选择历史会话即可查看或继续生成规则；启动 Mock 不需要重新抓包。
- 「导出 JSON」用于归档，包含会话、连接、完整已保存事件、关联和回放规则，字节字段使用 Base64。当前没有把该 JSON 重新导入为录制会话的入口，不要把它当成可直接恢复的数据库备份。
- 使用 `--db` 启动时，录制保存在指定数据库。备份 SQLite 数据库建议退出 TestTool 后复制，避免遗漏仍在 WAL 中的数据。
- 原始 TCP 片段中包含重传副本，业务消息中包含重组结果，因此“全部消息”条数不等于交易笔数。
- JSON 导出和删除等操作应等待录制、回放、文件任务结束；同一录制页同时只执行一个此类后台任务。

## 13. 常见问题排查

| 现象或提示 | 优先检查与处理 |
| --- | --- |
| 未找到 TShark | 「本地 TShark」是否是本机可执行文件路径；终端运行 `--version` 是否成功 |
| SSH 找不到 tcpdump | 「远端 tcpdump」填写远端实际路径，检查 SSH 非交互环境的 PATH |
| Permission denied、公钥认证失败 | 先在终端使用同一用户名、端口、私钥测试；检查 ssh-agent 和服务端密钥授权 |
| 主机密钥校验失败 | 先在终端确认目标主机及指纹，处理 SSH 已知主机配置；程序不会自动忽略校验 |
| tcpdump 权限不足 | 确认该账户直接执行 tcpdump 抓包有权限；仅能 sudo 成功不等于界面能够成功 |
| 本机提示 CAP_NET_RAW 或网卡权限不足 | 配置本机采集权限；SSH/文件导入不需要本机网卡权限 |
| 有业务但采集数为 0 | 网卡是否正确、端口是否填服务端端口、IP 过滤是否匹配、采集机器是否能看见流量 |
| 显示未捕获此方向 SYN | 开始抓包前连接已经建立，或握手包漏采；让测试连接在采集启动后新建，再录一遍 |
| 有 TCP 片段，没有正常交易 | 检查协议、长度头、分隔符、编码；确认没有 TLS 或 HTTP/2 |
| 长度头无效或报文过大 | 核对头是 ASCII 十进制、宽度正确、长度是否只含正文；也可能从连接中途开始采集 |
| 一直等不到完整报文 | 连接关闭分帧尚未观察到 FIN，或分隔符/长度头配置与实际协议不同 |
| 请求配错响应 | 检查是否并发、乱序或含主动推送；为 JSON 报文配置唯一关联字段，重新采集/导入 |
| JSON 流水号相同但没有自动配对 | 检查路径、编码、值类型、是否同一连接；同值并发存在歧义时不会猜测 |
| 存在序列缺口或抓包截断 | 检查网卡丢包、抓包范围、snaplen；文件采集用 `-s 0`，IP 分片场景扩大采集范围 |
| HTTPS/WSS 只有密文 | 当前不解密 TLS，不能从密文生成明文响应；需要另行提供能够获得明文的数据来源 |
| 已保存规则但 Mock 返回 404/不命中 | 核对协议、HTTP 方法和完整路径、正文匹配字段、消息类型；修改规则后重启 Mock |
| 多条规则命中报错 | 删除重复规则、调整生成时匹配字段，或按测试目的选择连接内顺序策略 |
| Mock 返回旧流水号 | 配置 JSON 回填字段，确认请求字段和响应父级路径存在；重启 Mock |
| Mock 无法启动 | 端口是否已被业务服务占用，监听地址是否属于本机，有无完整回放规则 |
| 无法生成客户端/固定 Mock | 检查交易是否完整及文本转换限制；分隔符 TCP、二进制 WS 等使用录制页 Mock |
| 看不到较早的交易 | 页面展示最近 500 条，归档可导出全部已保存数据；建议按接口和场景分批录制 |

## 14. 当前能力边界和容量

| 项目 | 当前行为 |
| --- | --- |
| 支持的传输与业务协议 | TCP、HTTP/1.1 明文、无压缩 WebSocket |
| 不直接解析 | UDP、HTTP/2、CONNECT 隧道、TLS 明文解密、WebSocket permessage-deflate |
| TCP 重组 | 按连接区分端口复用，支持乱序、重传去重、序列号回绕和半关闭；无法凭空补回丢失数据 |
| 被动采集连接数 | 单次最多 512 条连接，不是仅计算当前活跃连接 |
| 代理并发 | 最多 200 个同时连接 |
| 单条业务报文 | 上限约 10 MB |
| 乱序缓存 | 单方向最多约 10 MB / 4096 个片段；全局解析缓存约 64 MB |
| 未响应请求 | 单连接最多 1000 条 |
| 后台持久化 | 有界队列，最多 512 个事件、32 MB 待写字节；溢出或写库失败会提示不完整 |
| 自动回放范围 | 收到请求后按规则返回响应；不自动重现主动推送、跨连接业务状态、完整场景编排或网络故障 |
| 原始数据归档 | 保存已捕获 TCP 负载与业务解析结果；需要完整 pcap 包文件时，在服务器单独录文件 |

本机实时模式会保留用于 IP 分片解析的相关流量再做端口筛选；SSH 模式先按端口/IP 过滤，带宽更可控，但后续 IP 分片可能被过滤。高负载时应检查采集端丢包统计，按接口和业务情况分批录制。

## 15. 推荐的日常使用流程

```text
确认端口、协议、分帧和关联字段
    ↓
检查本地 TShark、SSH 密钥与远端 tcpdump 权限
    ↓
先开始采集，再建立业务连接
    ↓
先录一笔，核对请求/响应和连接完整性
    ↓
分场景录制：成功 / 业务失败 / 空结果等
    ↓
停止并保存，检查 complete 交互
    ↓
生成客户端用例，或生成 JSON 匹配 + 流水号回填的回放规则
    ↓
对方不可达时启动 Mock，让测试调用方访问 Mock
    ↓
核对业务结果，保留数据库与 JSON 归档
```
